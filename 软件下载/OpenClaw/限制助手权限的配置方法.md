## 一、为什么光靠嘴上叮嘱不行

公开报道过的失控案例至少有两起：一位研究员把「动手前先确认」写进了对话，长对话触发上下文自动压缩后这条指令被挤掉，邮箱被助手批量清空；另一位把 iMessage 交给助手管理，结果被群发了几百条消息。中国国家互联网应急中心 2026 年 3 月的[风险提示](https://www.cert.org.cn/publish/main/11/2026/20260312144519429724511/20260312144519429724511_.html)也把「误操作」与「提示词注入」列为已知风险。结论一致：**对话里的约束会丢，配置里的约束不会**。

下面的配置写在主机的 `~/.openclaw/openclaw.json`（默认位置，字段名以官方文档为准），改完重启服务生效。

## 二、命令白名单：只放行用得到的命令

把执行策略从「都能跑」改成「只许跑列出来的」：

```json5
{
  security: {
    exec: {
      mode: "allowlist",
      allowed: ["git", "node", "python3", "ls", "cat"],
      denied: ["rm -rf", "sudo", "chmod 777"]
    }
  }
}
```

- 优先 allowlist（白名单）而不是 denylist（黑名单）：黑名单总有漏网的写法；
- 起步只放行查看类命令（`ls`、`cat`、`grep`），跑顺了再按需加；
- 手机端报 `SYSTEM_RUN_DENIED` 多半就是被这一层拦了，属正常防护。

## 三、文件读写边界：别给整个家目录

```json5
{
  security: {
    fileSystem: {
      allowRead: ["~/.openclaw/workspace", "/tmp"],
      allowWrite: ["~/.openclaw/workspace", "/tmp"],
      denyWrite: ["~/.ssh", "/etc"]
    }
  }
}
```

把可写范围锁在助手自己的工作区里，系统目录、密钥目录一律放进 `denyWrite`。

## 四、破坏性动作加一道确认

在助手工作区的说明文件（`AGENTS.md`）里写死安全规则，同时保留上面的技术限制，两道一起上：

```markdown
## Safety Rules
- 删文件用回收站，不用 rm，动手前先问我。
- 发邮件、发消息、发帖必须先给草稿等我确认。
- 改系统配置文件之前必须先说明计划。
```

注意：这套话术本身也可能在长对话里被压缩掉，所以它只能当第二道防线，白名单才是底座。

## 五、记忆与子代理的隔离

- 每个助手实例用自己的记忆目录，别多个实例共用一份 `MEMORY.md`；
- 定期翻工作区里它自己写下的记忆文件，看看它记了什么、有没有走偏；
- 可以把记忆文件对子代理设成只读，只有主代理能写。

## 六、群聊与外部内容都是不可信输入

- 群聊里助手能看到所有人的消息，也可能跟着陌生人下的指令走——敏感操作只认你自己的账号；
- 网页、文档、邮件正文里可能藏着「忽略之前的指令」这类注入内容，让助手处理外部内容时保持小权限；
- 插件（skills）只从可信来源装：官方风险提示里专门点名过恶意插件，装前核对来源与签名，别开来源不明的自动更新。

## 七、补丁别拖

项目已公开曝出过多个中高危漏洞（2026 年初就有浏览器中继类的漏洞，修复随后续版本发出），保持版本更新是成本最低的一道防线，更新注意事项见 [常见问题排查.md](常见问题排查.md) 的更新一节。

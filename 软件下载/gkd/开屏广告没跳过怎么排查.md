# GKD 开屏广告没跳过怎么排查

> 无障碍开了、订阅也加了，某个应用的开屏广告还是原样播完 —— 按本篇的顺序排查，多数卡点出在规则覆盖和限流参数上。

「不跳」不是一个原因，从设置没勾到规则过时都有可能。下面的排查顺序按出现频率从高到低排，每一步都给出明确的判断方法，走完基本能定位到是哪一环的问题。

## 一、排查顺序总览

| 步骤 | 判断什么 | 怎么判断 |
| --- | --- | --- |
| 1 | 该应用的规则组有没有启用 | 进订阅页看对应应用的开关 |
| 2 | 订阅是不是最新版 | 订阅页手动检查更新 |
| 3 | 规则到底覆盖没覆盖这个应用 | 抓快照看 GKD 有没有识别到跳过按钮 |
| 4 | 规则是不是触发过又被休眠了 | 对照限流参数的含义 |
| 5 | 是不是界面事件根本没通知到 GKD | 特征：flutter/webview 页面，其他规则都正常 |
| 6 | 是不是后台被杀了 | 症状与处理见[后台保活与耗电优化](后台保活与耗电优化.md) |

## 二、前三步：最常见的三个原因

**第一步，规则组没启用。** 默认订阅装好就在，但里面的规则组要你手动按应用勾选。很多「我订阅了怎么不跳」最后发现是那个应用的组根本没开。回去把对应应用的组勾上，或先开「开屏广告」这类全局组（步骤见[订阅规则添加方法](订阅规则添加方法.md)）。

**第二步，订阅过期。** 应用改版后广告形态会变，旧规则跟不上新样式。进订阅页手动检查一次更新，让规则库拉到最新。

**第三步，用快照确认识别情况。** 这是分水岭的一步：在开屏广告出现时抓一份快照（怎么抓见[快照捕获与规则调试](快照捕获与规则调试.md)），然后看 GKD 有没有识别到那个跳过按钮：

- **完全没识别到** → 说明现成的规则不覆盖这个应用的这个界面。两个选择：换个订阅源试试，或把快照链接提给订阅作者等适配 —— 应用更新导致旧规则失效后，社区通常几天内会跟进；
- **识别到了但没点** → 继续往下查限流参数。

## 三、规则触发过但被「休眠」了

GKD 的规则自带防误触机制，触发过一次后会按参数休眠一段时间 —— 现象是「刚才还跳，同一界面再进去就不跳了」。本地规则里这几个参数决定休眠行为（远程订阅的规则也是同一套机制）：

| 参数 | 含义 |
| --- | --- |
| `actionMaximum` | 最大执行次数，达到后休眠（开屏广告类规则常设 1：一次启动只点一次） |
| `matchTime` | 规则被唤醒后只在限定时长内参与匹配，超时休眠 |
| `resetMatch` | 什么时候重置上面两个计数：`activity`（界面刷新时）/ `match`（从不匹配界面切到匹配界面时）/ `app`（重新进入应用时），默认 `activity` |
| `actionCd` | 两次执行之间的冷却，默认 1000 毫秒 |

判断方法：把这些参数当「刚开机要重新数」的逻辑看 —— 比如某应用规则 `resetMatch: 'app'`、`actionMaximum: 1`，那么同一次留在应用里反复杀掉广告再进是正常的，退出应用重进就会重新生效。如果你期望的触发频率和参数行为对不上，改自己写的规则参数即可；订阅里的规则动不了，只能反馈作者。

## 四、界面事件没送到：flutter/webview 类页面

GKD 靠监听系统无障碍事件感知「界面变了」，但官方文档明确说明：部分基于 flutter 或 webview 开发的应用和页面，界面内容变了却不会通知系统触发事件 —— GKD 根本不知道该开始匹配。识别特征：这个应用里所有规则都哑火，而其他应用一切正常。

这类界面要靠规则里主动查询机制（`matchDelay` 一类）去弥补，属于规则作者要适配的范畴 —— 你这边能做的就是确认到这一步之后，抓快照反馈给订阅作者，不要反复开关无障碍重试，那不会有用。

## 五、都排完了还是不跳

按 1→6 走完仍未解决，剩下的基本是「该应用用了难处理的广告形态」这一类，交给社区：快照 + 简述场景（什么应用、什么界面、期望什么动作）提给订阅仓库，比换十遍设置都有效。等待适配期间，把该应用的规则组开着不影响别的应用 —— 规则不匹配时它只是空转，代价可忽略；真正要留意耗电的场景在[后台保活与耗电优化](后台保活与耗电优化.md)里有单独说明。

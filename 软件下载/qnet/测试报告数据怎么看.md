## 一、报告从哪来、什么时候生成

QNET 的【设置】切页里除了「网络抓包」，还有一个**测试报告**开关 —— 它和抓包一样是**勾选后再启动弱网时生效**：先勾开关，再点启动，测试结束（停止弱网）后自动生成文件。跑的过程中才勾，这一轮不会有报告。

生成两个文件：

- **csv**：测试过程中的全部数据，一行一个包，适合拿去做统计或用表格软件处理；
- **html**：汇总好的图表页，**用手机浏览器直接打开**就能看，不用导电脑。

和抓包文件一样，保存位置在【设置】里对应的路径下（官方手册标的是 QNET 的应用缓存目录，抓包文件在 `/sdcard/Android/Data/com.tencent.qnet/cache/` 下，报告在同一片区域找）。报告与抓包可以同时开：报告给结论（延时涨了多少、丢了多少），抓包给现场（那个包到底发生了什么）。

## 二、csv 每一列是什么

官方手册对列的定义如下（照它翻成白话）：

| 列名 | 含义 |
| --- | --- |
| `id` | 每个包的序号 |
| `pcap_id` | 对应抓包文件里的包序号 —— **数量可能少于 pcap 里的包数**，对不上属正常 |
| `is_up_or_down` | 1 = 上行（发出去），0 = 下行（收进来） |
| `remote_ip` | 这个包发往的目标 IP |
| `create_time` | 生成时间，单位毫秒 |
| `delay_time` | 这个包的延时，单位毫秒 —— 官方注明**与实际时间可能存在一定误差，和当前网络有关** |
| `packet_length` | 该 IP 包的大小，用来统计流量 |
| `is_lose` | 1 = 这个包被 QNET 丢掉了；0 = 没丢 —— 但上行包在真实网络传输中也可能被丢，所以「没丢」不代表对方一定收到 |

两个最容易读错的点：

- **`delay_time` 不是你填的参数值，是实测值**。你在模板里填 200ms，实际延时会在 200ms 上下浮动（QNET 会探测真实网络后动态叠加），拿 csv 一算平均值和设定值对不上是正常的。
- **`is_lose=0` 只代表 QNET 没丢它**，上行包在离开手机之后还可能被真实网络丢掉 —— 判断「服务端没收到」不能只看这一列，要结合抓包与应用日志。

## 三、html 报告的三张图与三个数

html 页面给你的是**趋势和汇总**，比逐行看 csv 快得多：

**三张波形图**：上行延时、下行延时、丢包趋势。看图时对着你设置的模板参数找规律 —— 周期弱网（放行/弱网交替）应该在图上看到方波状的延时跳变；Burst 类型应该看到恢复瞬间的尖峰；随机丢包则是均匀散落的丢包点。

**三个汇总数**：平均时延、丢包率、流量统计。这组数适合直接记进测试结论，比如「在 3G 模板下平均时延 xx ms、丢包率 x%」，作为版本间的对照基线（数值随环境波动，对照要在同样模板、相近网络下做）。

## 四、报告、抓包、悬浮窗各看什么

三样东西解决三个问题，配合用：

| 你想知道 | 看哪里 |
| --- | --- |
| 弱网整体有多差、能不能验收 | html 报告的三图三数 |
| 某个时刻具体发生了什么 | 抓包 pcap（配合报告里的 `create_time` 定位时刻） |
| 此刻正在什么参数下跑 | 信息悬浮窗（实时延迟、ping、当前模板参数） |

举例：用户反馈「重连后卡住」→ 先在 html 的丢包趋势图上找到断开时段 → 用 `pcap_id` 对到抓包文件里的具体包 → 在 Wireshark 里看重连握手花了几轮。分析口径见 [悬浮窗控制与抓包导出教程.md](悬浮窗控制与抓包导出教程.md)，参数含义见 [弱网模板参数设置教程.md](弱网模板参数设置教程.md)。

要自动化地拉起这些开关，用 adb 的 `dump_pcap` 等参数，见 [adb命令自动化弱网测试教程.md](adb命令自动化弱网测试教程.md)。

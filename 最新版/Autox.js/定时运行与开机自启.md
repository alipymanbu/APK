# 定时运行与开机自启

> 「每天早上八点自动签到」这类需求，卡点从来不在脚本本身，而在「怎么让它到点自己跑起来」。本篇讲定时任务的几个实现层次、为什么后台保活是成败关键，以及锁屏密码带来的硬限制。

## 一、三条定时路线

| 路线 | 适用 | 前提 |
| --- | --- | --- |
| 应用内定时任务 | 每天固定时间跑脚本 | 应用活着、后台保活到位 |
| 脚本内定时器 | 脚本运行期间的周期动作 | 脚本本身被启动着 |
| Tasker 等外部工具联动 | 复杂条件触发（到地点、连上某 Wi-Fi） | 安装并配置 Tasker |

三条不冲突，常用组合是「应用内定时任务到点启动脚本 + 脚本内部再用定时器做循环动作」。

## 二、应用内定时任务

Auto.js 家族的应用内定时入口大同小异：在脚本列表里找到目标脚本的菜单（通常是右侧菜单按钮 → 「更多」），里面有「定时任务/任务」一类选项，可以设置定时时间、开机自动运行等条件。你的版本菜单位置可能不同，找不到就翻一遍菜单或看应用内置示例。

设置好之后，成败取决于一件事——**应用必须还活着**。定时任务不是系统的闹钟，到点时是 Autox.js 自己把脚本拉起来；如果应用早被系统杀掉了，任务到点也没人执行。所以先把 [权限设置与无法运行排查.md](权限设置与无法运行排查.md) 第三节的保活三件事做全：

1. 电池优化白名单（不受限制）；
2. 最近任务上锁；
3. 关掉厂商的省电/纯净模式。

验证方法很简单：设一个两分钟后的定时任务，然后回到桌面别动手机（或直接锁屏），等它触发。触发了才算通，触发不了回头查保活。

## 三、脚本内的定时器

脚本一旦跑起来，内部的周期动作用定时器实现，语义和网页 JavaScript 一致：

```javascript
// 每 10 秒做一次检查
let id = setInterval(function () {
    toast("轮询中");
}, 10000);

// 60 秒后停止轮询
setTimeout(function () {
    clearInterval(id);
    toast("轮询已停止");
}, 60000);
```

这套写法适合「脚本常驻、周期干活」的场景（比如监控某个界面状态）。注意两点：

- 定时器回调里报错不会自动停脚本，建议回调里套一层 `try...catch`，把错误写进日志；
- 纯 `while(true) + sleep` 也能实现轮询，但定时器写法更清晰，也方便中途取消。

## 四、亮屏与锁屏：硬限制要想在前面

定时任务在夜里触发时，手机多半锁着屏。这一层的现实是：

- 用 `device.wakeUp()` 一类函数可以**点亮屏幕**；
- 但 Autox.js **没有解锁屏幕的能力**——设了锁屏密码的手机，到点后停在密码界面，脚本看不到也无从操作。

所以「夜里无人值守跑任务」的常见做法要么去掉锁屏密码（安全自负），要么把触发时间安排在手机活跃使用的时段。有锁屏密码还想定时跑，这条路在系统层面就走不通，别在这上面耗时间。

另一个系统级限制同样要记住：从 Android 10 起，应用在后台无法自行拉起界面（部分国产系统更早收紧），所以把「启动带界面的应用」写进定时脚本时，后台状态可能点了没反应——把后台弹出界面、自启动权限都开上，能缓解大半。

## 五、打包应用的定时与自启

如果你的脚本是打包后的独立应用（见 [把脚本打包成独立应用.md](把脚本打包成独立应用.md)），定时逻辑要打进应用里自己实现（脚本内定时器 + 常驻），打包配置里的「开机自启动」勾选项可以让它在重启后自动恢复——勾选项名称与位置以你版本的打包界面为准。接收方的设备同样要做保活三件事，否则和宿主环境一样会被杀。

需要「到点、到地点、连上某网络」这类更复杂触发条件的，用 Tasker 联动：Autox.js 可以作为 Tasker 的插件被调用，由 Tasker 负责触发、脚本负责执行。

## 六、排查清单

定时任务到点没反应时，按顺序查：

| 步骤 | 检查什么 |
| --- | --- |
| 1 | 应用本身还活着吗（先手动打开确认没被杀） |
| 2 | 保活三件事做完了吗（白名单、上锁、关省电） |
| 3 | 定时时间设的是 24 小时制吗（14:00 不是下午 2 点写法错误） |
| 4 | 手机锁屏了吗（有密码就是硬墙，见第四节） |
| 5 | 脚本第一行是否依赖网络或截图（后台状态这些可能要重新授权） |

还是不行的，把手动运行同一个脚本的结果对照 [常见问题与报错处理.md](常见问题与报错处理.md) 排查——定时跑不通时，先确认手动能不能跑通。

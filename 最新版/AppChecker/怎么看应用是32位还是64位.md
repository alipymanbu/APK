「这个应用是几位的」是很多人装 AppChecker 的直接原因。答案来自应用里打包的原生库目录名，而不是某个可以凭体积、界面猜出来的属性。本篇把判断依据、在应用里的查看位置和常见误判一次讲清。

## 一、先分清一件事：不是所有应用都分 32 / 64 位

按 Google 官方的口径，如果一个应用**只用 Java / Kotlin 写**、没有引入任何原生库（`.so` 文件），那它本身就不存在 32 位还是 64 位的问题，在 64 位设备上照常运行。只有打包了原生库的应用，才会有「有没有 64 位版本」这个说法。

所以要判断的其实是：**这个应用有没有提供 64 位版本的原生库。**

## 二、判断依据：原生库的 ABI 目录名

原生库按 ABI（应用二进制接口）分别存放，目录名就是判据。照着下表对号入座即可：

| 应用里出现的名字 | 指什么 | 位数 |
| --- | --- | --- |
| `armeabi-v7a` | ARM 架构 32 位 | 32 位 |
| `arm64-v8a` | ARM 架构 64 位 | 64 位 |
| `x86` | Intel / AMD 架构 32 位 | 32 位 |
| `x86_64` | Intel / AMD 架构 64 位 | 64 位 |

`aarch64` 是 ARM 64 位架构的另一种写法，和 `arm64-v8a` 指同一件事，看到它同样按 64 位算。

这些名字在安装包里的位置是 `lib/` 目录下的一级子目录（原生库是里面的 `.so` 文件）。所以「打开 `lib` 看有几个子目录、叫什么名字」就是最原始的核法，AppChecker 的原始信息里列出来的正是这一层结构。

结论按这个顺序读：

1. 应用里**没有任何**原生库目录 → 纯 Java / Kotlin 应用，不涉及位数；
2. 有 32 位目录、**没有** 64 位目录 → 只有 32 位版本；
3. 出现 `arm64-v8a` 或 `aarch64` → 支持 64 位。

## 三、在 AppChecker 里从哪看

1. 打开 AppChecker，在应用列表里点开你要查的那个应用，进入它的详情页。详情页会给出这个应用的架构 / 位数标注，这是最快的入口。
2. 想要自己核一遍，就在详情页里找**「原始信息」一类的入口**（不同版本菜单措辞会有差异，也可能写作 raw info 之类），进去后看清单里列出的原生库或 ABI 名称，再按上一节的规则判断。
3. 手机自带的应用商店页面有时也会标注「64 位」「32 位」，两个地方对不上时，以 AppChecker 读到的本机安装包为准 —— 商店页信息由商店维护，可能与已安装版本不一致。

列表或详情页上的 32 位 / 64 位徽标，在部分机型上显示得比较小，这是已经被用户提过的细节，不影响判断，点进详情页看文字更稳。

## 四、为什么要关心位数

- **更新与上架**：Google Play 要求含原生库的应用在提交新版本时，必须为每个支持的 32 位架构同时提供对应的 64 位版本。也就是说，只打包 32 位库的应用连新版都提交不上去 —— 长期停在 32 位的应用，基本都是多年没有维护的老应用。
- **存量分发没被禁**：官方并没有停止支持 32 位，也明确表示会继续向 32 位设备分发应用，所以「32 位应用马上全都不能装了」的说法不成立。真正的分界在设备一侧：只支持 64 位的设备装不了只有 32 位库的应用。
- **性能**：64 位版本能用到更多的寄存器与更大的地址空间，对图形、音视频、压缩这类重计算场景更有利，收益大小取决于应用本身。

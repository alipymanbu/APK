# NoActive 冻结方式怎么选：API、V2、V1、KILL 对照

> NoActive 提供 API、V2、V1、KILL 四种冻结方式，选错方式是「装了没效果」的头号原因。本篇给你按内核对号入座的选法与兜底手段。

## 一、先给结论

- 内核够新的机器：选 **V2** 或 **API**。官方仓库的建议顺序也是 API、V2 优先，其次才是 Kill。
- 4.19 内核的小米系（MIUI / HyperOS）：选 **V1**。
- 其他 4.19 及以下内核：选 **KILL** 兜底。
- 判断依据只有一条：你的内核支持哪种，以及实测哪种能把应用冻结住。

## 二、四种方式对照

| 方式 | 机制一句话 | 适合谁 | 要注意的坑 |
| --- | --- | --- | --- |
| API | 调用系统自带「暂停执行已缓存」的 API，按内核支持自动处理 | 内核新、不想折腾的机器 | 官方标注「API 存在不可控性」，行为随系统版本变化 |
| V2 | Cgroup Freezer V2，谷歌原生的后台冻结机制 | 内核 5.0 及以上（部分厂商把它移植到了 4.19） | 兼容性好、效果统一，公开教程普遍首推 |
| V1 | Cgroup Freezer V1 | 4.19 内核的 MIUI / HyperOS / RealmeUI / ColorOS | 非 MIUI 设备曾有内存泄露问题；3.2 起加了防泄露补丁降低影响 |
| KILL | 用信号方式处理进程 | 任何内核都能用，最后的兜底 | 内存吃紧时系统可能把冻结的进程全部解冻；进程仍存在，回到前台可能重载（官方仓库提到 Kill 存在这种 bug） |

KILL 方式的两个坑是机制自带的：它是「信号」而非「冻结器」，所以内存压力一大系统就把进程全放出来；放出来后应用回前台就可能重载。能用 Freezer（V2/V1）就用 Freezer。

另外按用户社区反馈，有的版本会把 Kill 细分成 KILL19 / KILL20 两档，或者多一档「自动」让系统自己识别——分档只是信号取值不同，哪个实际能冻住就用哪个；「自动」档有识别出错的反馈，选了它没效果时记得手动指定。

## 三、按你的内核对号入座（社区教程整理）

| 你的情况 | 建议方式 |
| --- | --- |
| 内核 5.0 及以上 | V2（或 API） |
| 内核 4.19 的 MIUI / HyperOS / RealmeUI / ColorOS | V1 |
| 其他 4.19 及以下 | KILL |

这份对照来自社区教程整理，最终取决于你机器的内核实际支持了什么；同一台机器上把几种方式各试一遍，哪个能把应用冻结住就用哪个。

## 四、切换方法与验证

1. 打开 NoActive，进右上角设置，找到「冻结方式」。
2. 选定后回到「运行列表」：开一个应用再退到桌面，看它是否显示「已冻结」。
3. 刚切换完不生效，先重启一次再看。
4. 还是全都没被冻结 → 往下看兜底手段，或按 [常见问题与故障排查.md](常见问题与故障排查.md) 排查。

## 五、都不生效时的兜底

- **提权模式**：官方仓库说明，部分机型的系统框架没有权限读写 Freezer 目录，这种机器可以在设置里开启提权模式再试。
- **冻结日志报 error**：官方 README 的建议是直接换 Kill 方式试。
- **Kill -19 + 放行 SELinux 策略**：官方 Gitee 仓库给出的最后手段——把冻结方式切到 Kill -19，然后每次开机后执行一次下面两条命令：

```bash
su
magiskpolicy --live "allow system_server * process {sigstop}"
```

这条命令的效果重启后不保留，所以每次开机都要重新执行；嫌麻烦可以把它写进开机脚本，具体做法各 root 管理器不同，按你用的那个查。

# Gloom 加载失败和请求次数限制怎么排

> 本篇讲一种「不是坏了、也没有设置可改」的加载失败：手机上刷得太勤，被 GitHub 的接口次数限制拦住了，以及怎么等回来、怎么少撞。

这一篇解决一种最容易误判的故障：网络正常、也登录着，可用一阵子之后页面开始反复加载失败，停一会儿又自己好了。这不是应用坏了，也不是账号出问题，而是短时间内向 GitHub 发的请求太多、被临时限流了。下面讲怎么确认是不是这一类、怎么等回来、平时怎么少撞。

## 一、先分清三种「打不开」

这三种现象长得像，解法完全不同，第一步是把它们分开：

| 现象 | 判断依据 | 属于哪一类 |
| --- | --- | --- |
| 什么都刷不出来，浏览器也打不开 GitHub | 换浏览器试同一时刻同样打不开 | 网络问题，见 [常见问题与排查.md](常见问题与排查.md) |
| 别的页面正常，某几页反复失败 | 隔一会儿又能用，过一阵又失败 | 接口次数被限，本篇讲的就是这个 |
| 单个文件或仓库打开就卡住 | 换个小仓库立刻正常 | 那个页面本身内容大，不是限制 |

区分第二类的要点是**反复性**：它不是一直坏，而是「用一阵子开始失败，停一会儿又好了」。这是次数限制最典型的样子。

## 二、这个限制是什么

你在首页和仓库页看到的每一块内容，都是拿一次对 GitHub 的请求换来的。GitHub 对这类请求按小时给了配额，用超了就先拒绝你一段时间。按 GitHub 官方文档当前的口径：以用户身份授权访问时，配额是**每小时 5000 点**（按点数计费，不同内容消耗的点数不同）；未登录的匿名请求配额要低得多。

| 你的状态 | 大致配额 | 说明 |
| --- | --- | --- |
| 已登录授权（Gloom 的正常用法） | 每小时 5000 点 | 同一账号在别处用的量也算在里面 |
| 未登录 | 低得多 | 这也是一登录就顺畅很多的原因 |

两点要记住：

- **配额是按账号算的，不是按设备算的**：同一个账号在手机、网页、电脑客户端上刷的量，都在同一个池子里扣。
- **限制不等于封号**：它是临时的，过了窗口自动恢复，不需要你改密码或重新登录。

各接口的具体数值以 GitHub 官方文档当时公布的为准，官方调整过不止一次。

## 三、撞上之后按这个顺序做

1. **先停手**：不要再连着下拉刷新、来回进出大仓库，越刷恢复得越慢。
2. **等窗口过去**：按小时计的那种限制，等几十分钟到一小时基本就回来了。
3. **确认是不是账号层面的量太大**：回忆一下是不是同时开着网页端和别的客户端在一起刷同一个账号。
4. **回来之后降节奏**：翻列表别一路快速下拉到底，看准了再点进去。

如果等了一小时仍然完全不行、而浏览器同一时间能正常打开 GitHub，那多半不是配额问题，回到 [常见问题与排查.md](常见问题与排查.md) 按网络那条查。

## 四、日常怎么少撞

- **别把「下拉刷新」当翻页用**：连着刷十几次是消耗配额最快的方式。
- **同一个账号别在太多地方同时用**：手机、平板、网页端各开一个还都开着自动刷新，很容易顶到上限。
- **大仓库不要反复进进出出**：每次进入都要重新拉一遍列表和文件信息。
- **翻目录时按需打开**：一路把所有子目录都点开一次，等于把整个仓库跑了一遍。

这些都是「少花配额」的习惯，不是必须遵守的规则 —— 平时正常用，很难碰到上限；只有在连续大量浏览时才会遇到。

## 五、和网络问题怎么区分

最后给一个更省事的判据：**同一时刻打开浏览器访问 GitHub**。

| 浏览器的情况 | 结论 |
| --- | --- |
| 能正常打开 | GitHub 侧到你的网络是通的，问题在应用这边的请求被限制了 |
| 同样打不开 | 网络问题，去排查网络那条 |
| 时好时坏 | 网络不稳定，和配额无关 |

用这一招基本不用猜：能正常打开就按第三、四节处理配额；同样打不开就去 [常见问题与排查.md](常见问题与排查.md) 查网络；时好时坏属于网络不稳定，等网络状况好转自然恢复。分不清某次失败到底属于哪一类时，再看一眼第一节那张表 —— 反复性是限流最明显的特征。

## 一、一个仓库页里都有什么

点进任意仓库，能拿到的东西大致是这几块，对应 GitHub 网页端的主要栏目：

| 区域 | 你能做的事 |
| --- | --- |
| 文件列表 | 按目录层级翻，进到任意一级；列表跟着当前选的分支或标签走 |
| 文件内容 | 打开单个文件看内容，代码按语言着色；Markdown 文件直接渲染成排版后的效果 |
| 提交记录 | 看这个仓库历次提交的时间和说明，用来判断项目最近还动没动 |
| 贡献者 | 谁在维护这个项目、大致贡献比例 |
| Issues | 看 issue 列表、进单条看正文和讨论 |
| Pull Requests | 看 PR 列表、进单条看改动说明与讨论 |
| Releases | 看发布记录、版本号、发布时间，以及这一版附带的文件清单 |
| 其他信息 | 语言构成、许可协议、分支与标签、Fork 情况 |

想快速判断一个项目靠不靠谱，看三个地方就够：**最近一次提交或发版的时间**、**Issues 里有没有人回**、**许可协议是不是允许你按需要的方式使用**。

## 二、看代码时的实际体验

- **它是阅读器，不是编辑器**。可以翻目录、开文件、看高亮，但改代码、提交、建分支这些事它不做。
- **长文件要有心理预期**。手机屏幕窄，几千行的单文件靠滑动读会很吃力，找具体某段代码建议用网页端的搜索，或者把仓库拉到电脑上看。
- **Markdown 会渲染**。README、文档类文件打开就是排版好的样子，不是一堆符号；这比在浏览器里眯着眼看原始文本舒服。
- **分支和标签要先切对**。打开的文件列表属于当前选中的那个分支 —— 找不到某个文件时，先确认你切到的是不是 `main` 之外的正确分支或某个标签。

## 三、Issues 和 Pull Requests 能读到哪一步

这两块是「读得到、动不了」：

- **能看**：列表、单条的正文、所有评论和讨论过程。
- **能加表情回应**：给 issue、PR 或评论点一个 reaction，这是应用内少数几个写操作之一。
- **不能做**：新建 issue、在 issue 下写评论、新建或合并 Pull Request、审核代码。这些都需要回 `github.com` 网页端。

所以真实用法是这样：**白天在手机上把 issue 读完、把要回复的点记下来，回电脑时一次性处理**。想指望在通勤路上把 issue 直接回完，这个客户端给不了。

## 四、Releases 这块值得单独用

Releases 是判断项目状态最快的地方，也是找可执行文件的地方：

1. 进仓库页的 Releases 区域，看最新一条的时间和版本号；
2. 展开这一条，看它附带了哪些文件（源码包、编译好的产物等）；
3. 需要下载时，注意附件通常是跳到浏览器完成下载的，能不能在应用内直接把附件下下来，以你装的这版实际显示为准；
4. 版本号命名规则各项目不同，`v` 前缀、日期编号、语义化版本都有，别拿两个项目的编号直接比大小。

有个细节值得留意：**发版频率低不等于项目死了**，有些项目常年只在自己的分支上提交、不发版；反过来，发版勤也可能是自动打版本号。看提交记录比看版本号更接近真相。

## 五、能改的东西只有三类

在这份客户端里，你对 GitHub 账号的写操作集中在这三样：

| 操作 | 在哪做 |
| --- | --- |
| star / 取消 star | 仓库页 |
| 关注 / 取关某个人 | 用户主页 |
| 给 issue、PR、评论加表情回应 | 对应的详情页 |

除此之外的改动（发 issue、写评论、合并 PR、改仓库设置），都要回网页端。把这一点当成它的使用边界，用它该干的事，就不会觉得处处不顺手。

## 六、几个实际的使用场景

- **查一个项目的授权方式**：进仓库看许可协议，几秒钟的事，不用开电脑。
- **确认某个版本什么时候发的**：看 Releases 的时间，比翻新闻可靠。
- **顺手收藏**：看到值得留的项目就 star，回到电脑上还能在 star 列表里找到。
- **判断还要不要用某个库**：看最近提交时间 + issue 区回复情况，两项都冷，基本可以换替代品了。

这些场景之外的需求，比如读源码找某个函数的实现，手机上效率一定低于电脑 —— 不是应用的问题，是屏幕和输入方式的限制。

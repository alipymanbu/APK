## 一、先看状态码，再决定动哪里

LastChat 只是把服务商返回的错误透给你，**改配置要在提供商里改，改内容要在对话里改**。对照表（以服务商返回的原始状态码为准，OpenAI 官方文档与各家 OpenAI 兼容网关的口径基本一致）：

| 状态码 | 含义 | 你该动哪里 |
| --- | --- | --- |
| 400 | 请求格式错误，或上下文超出模型上限 | 精简对话内容 / 换长上下文模型（见第三节） |
| 401 | key 无效、过期，或与 Base URL 不匹配 | 换 key、核对 Base URL |
| 403 | key 无权限，或令牌额度/分组被限制 | 去服务商后台看令牌额度与分组 |
| 404 | 接口路径不存在 | Base URL 少了 `/v1` 或多了路径，最常见 |
| 413 | 请求体过大 | 删掉超长附件/贴入的整份文件（见第三节） |
| 429 | 触发限流，或余额/配额用尽 | 先分清是哪一种（见第二节） |
| 500 / 503 / 504 | 服务商端故障、模型不可用、网关超时 | 等一会儿重试；持续则看服务商状态页 |
| 超时无状态码 | 网络不通或 Base URL 域名写错 | 查网络、查域名、查是否需要代理 |

**排查顺序永远是**：key → Base URL → 模型 ID → 接口格式 → 内容长度。这五样都对还报错，问题基本在服务商那侧。

## 二、429 要不要一直重试

429 有两种性质，处理完全不同：

- **偶发**：发十条错一两条，等几秒再来就成功。这是配额类接口的常态，不用改任何设置。
- **持续**：几十秒内条条 429。这时**别猛点重发** —— 失败的请求也照样计数，连续重发只会把窗口越堵越久。停手等 60 秒再发一条测试。

持续 429 的四种成因与对策：

| 被限的是 | 典型场景 | 对策 |
| --- | --- | --- |
| 每分钟请求数 | 连续快速发短消息 | 发慢一点，别连点 |
| 每分钟 token 数 | 长对话、长输出 | 缩短上下文（见第三节）或拆成多个对话 |
| 并发数 | 同时开多个对话/多设备共用一个 key | 减少同时在跑的会话 |
| 账号配额/余额 | 等一会儿仍条条 429 | 去服务商后台充值或等额度窗口刷新，重试无用 |

> [!NOTE]
> 服务商若在错误里给了 `Retry-After` 或限流说明，按它写的等；没给就按「停 60 秒再试」处理。把配额问题当成限流反复重试，是白花时间最多的那种错法。

## 三、内容太长：400 与 413

模型的上下文窗口是有限的，「历史消息 + 附件 + 提示词」加起来超了，返回 400 或 413。按这个顺序减：

1. **先删刚贴进去的大文件/整份文档** —— 1.4.6 起，二进制与超大文件本来就该放进工作区处理（见 [代码运行与联网搜索怎么用.md](代码运行与联网搜索怎么用.md)），别整份贴进输入框。
2. **再砍历史**：新开一个对话只带必要背景；或在助手里把 `contextMessageSize`（每次请求携带的最近消息数上限）从 `0`（全部历史）调到一个具体数值，直接决定每条消息花多少 token。
3. **还不够就换模型**：不同模型上下文长度差别很大，模型选择器里换一个上下文更大的，或在 [配置API接口与模型教程.md](配置API接口与模型教程.md) 里配第二个模型专门处理长文。
4. **输出侧**：单次回复的 token 上限（`maxTokens`）设得过高也会更快撞限，按需要调小。

## 四、请求发不出去 / 一直转圈

没有任何状态码时，问题在链路上，逐项排：

1. 手机网络能否打开服务商的官网（排除本机网络与代理问题）。
2. Base URL 是否完整：协议（`https://`）、域名、`/v1` 路径一个都不能少，也别多带一层。
3. 服务商是否只在特定网络环境下可用 —— 有的中转需要代理，能开网页不代表能通 API。
4. 换一个服务商卡片发同一条消息做对照：能通，说明是原提供商配置；都不通，先查网络。

仍定位不了，把「状态码 + 请求的模型名 + Base URL 的域名部分（key 打码）」三样带去服务商的支持渠道，比只说「用不了」有效得多。其余高频卡点见 [备份恢复与常见问题.md](备份恢复与常见问题.md)。

# microG 推送通知收不到怎么排查

> 本篇按「先看开关、再看电源、最后看应用注册」的顺序，把 microG 环境下收不到推送的原因过一遍，并给出每一步的判断依据。

推送是 microG 最常被用到的功能，也是出问题最多的一项。它要走完一整条链路：应用向 microG 注册、microG 拿着设备身份去 Google 那边登记、服务器发消息回来、消息再由 microG 转交给应用。任何一环断了，表现都是同一句话——通知不来。

## 一、第一步：确认那两个开关是开着的

microG 设置主界面上的这两项，缺一个推送就不通：

| 开关 | 作用 | 关掉的后果 |
| --- | --- | --- |
| Google 设备注册 | 给这台设备在 Google 侧登记一个身份 | 后面所有推送相关的动作都没有凭据可用 |
| Cloud Messaging | 接收并分发推送消息 | 应用即使注册上了也收不到消息 |

官方文档把「两个都打开」写成唯一被支持的配置。装完后如果只勾了一个，先补上，再重启一次。

## 二、第二步：看设置里有没有「已注册的应用」

打开 Cloud Messaging 那一项，里面会列出已经登记过的应用清单：

- **列表里没有你要的那个应用** → 它还没注册成功，走第三节；
- **有，状态却显示未连接** → 是链路问题，走第四节；
- **有，状态正常，但通知还是不来** → 问题多半不在 microG，走第五节。

这个列表是最省事的判据：它把「microG 这边有没有接到」和「应用那边有没有收到」分开了，不用靠猜。

## 三、第三步：应用没注册上的两种情况

**情况一，应用是在装 microG 之前就装好的。** 这是最常见的一种。应用在第一次运行时才会去注册推送，如果那时候机器上还没有 microG，它就注册失败了，之后不会自己重试——反而会一直尝试，白耗电。常规处理办法是**卸载后重新安装那个应用**，让它在新环境下重新走一遍注册流程。重装前记得先把应用内的数据备份好。

**情况二，应用装对了顺序，但注册被系统拦下。** 回头查两件事：microG 的权限给全没有（尤其是账号、后台相关的那几项），以及系统有没有额外的权限管理在拦它。

## 四、第四步：注册上了但连不上

按从易到难排：

1. **关掉电池优化。** 这是官方明确要求的一步。系统把 microG 冻结之后，那条长连接会断，消息自然收不到。设置 → 电池 → 电池优化 → 找到 microG 的服务组件 → 设为不优化。国内厂商的系统往往还要额外放开自启动与后台活动，逐项清单见 [后台被杀和耗电怎么处理.md](后台被杀和耗电怎么处理.md)；
2. **确认网络能到 Google 的服务器。** microG 的推送走的是 Google 那一套服务器，网络到不了那里时，应用列表里会长时间显示未连接。这一环与 microG 本身无关；
3. **手动触发一次重连。** 在拨号盘输入下面这个号码，是社区里流传多年的一个触发方式：

```text
*#*#2432546#*#*
```

它不一定在所有系统版本上都有效，属于先试一下的成本很低的动作；

4. **重启一次。** 改完开关、装完组件之后，很多状态要等重启才刷新。

## 五、第五步：microG 这边都正常，通知还是不来

到这一步，问题基本不在 microG 身上，按这几种情况分：

| 现象 | 判断 | 怎么处理 |
| --- | --- | --- |
| 只有某一个应用不来通知 | 该应用自己的推送实现或它的后台策略 | 去应用设置里检查通知权限、后台运行权限、自启动开关是否被系统关掉 |
| 一堆应用都不来，且网络正常 | 先怀疑服务本体版本过旧 | 更新 microG 服务本体再试 |
| 应用属于不用 FCM 的那一类 | 它可能走自家推送或走 UnifiedPush 这类开源替代 | 这类应用的推送不经过 microG，microG 侧怎么调都不会有变化 |
| 锁屏一段时间后集中收到一批 | 后台被系统限制 | 回到第四节第 1 条，把电池优化与自启动这两处都放开 |

## 六、把顺序固化成一张表

真出问题时按这个顺序走，能省掉大部分反复：

1. 两个开关是否都开着；
2. Cloud Messaging 列表里有没有这个应用；
3. 没有 → 应用是不是在装 microG 之前装的，是就重装；
4. 有但未连接 → 电池优化、网络可达性、重启，三步依次试；
5. 全部正常 → 去应用自己的设置里找原因，或者检查这个应用是不是根本不走 FCM。

如果第 5 步确认是应用层面就解决不了（例如它还额外要求设备完整性判定），参见 [哪些应用和功能用不了.md](哪些应用和功能用不了.md)。

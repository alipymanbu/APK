## 一、Java 运行时：跟着游戏版本走

启动器内置了三套 Java 运行时（OpenJDK 8 / 17 / 21，覆盖 32 位与 64 位设备），游戏版本对应关系如下：

| 游戏版本 | 需要的运行时 |
| --- | --- |
| 1.16.5 及更早 | Java 8 |
| 1.17 ~ 1.20.4 | Java 17 |
| 1.20.5 / 1.21+ | Java 21 |

正常情况下启动器会自动选对，你需要在设置里动手核对的时机只有两个：一是手动改过运行时之后新版本起不来；二是模组环境对 Java 有额外要求（个别模组对 Java 版本敏感）。选错运行时的典型症状是游戏进度条走完直接退回启动器，改回对应版本即可。

## 二、渲染器：按你的 GPU 挑

渲染器决定游戏画面跑在哪种图形接口上。选错最常见的结果是**黑屏**（进游戏后只有声音或直接卡死），选哪套也直接影响帧数上限：

| 渲染器 | 适合的设备 | 适合的场景 | 注意点 |
| --- | --- | --- | --- |
| GL4ES（默认） | 覆盖面最广，老机型也能跑 | 原版与多数老版本模组 | 老版本首选；1.21.1 及以上在此渲染器下曾出现画面全黑，需 Gladiolus 及之后的版本才修复 |
| Zink | 官方标注支持 Mali-Gx7 及以上、Adreno 6xx/7xx 系列 GPU 的新机型 | 新版本游戏、对兼容性要求高时 | 基于 Vulkan；不支持的 GPU 上开不了或直接报错 |
| LTW | 支持 OpenGL ES 3.0 的新机型 | 新版本 + Sodium/Iris 这类优化与光影模组 | 实现了 OpenGL 3.2 的一个子集，能跑此前只有 Zink 能跑的模组；光影支持有限，个别地图类模组（如 Xaero 系列）颜色可能异常 |

（更早的 VirGL 渲染器已在 Edelweiss 版本中移除，老教程里提到的可以忽略。）

换渲染器在启动器设置里一键切换，切换后重新启动对应版本生效。经验路径：原版先用默认 GL4ES；玩 1.17+ 遇到黑屏先换 Zink（设备符合的话）；要用 Sodium/Iris 加光影的再试 LTW。

## 三、内存分配：给游戏多少 RAM

启动器支持自动和手动两种内存分配：

- 不确定就交给**自动分配**，它会按设备内存估算一个可用值。
- 手动改的时候，不要拉到接近物理内存——系统本身和启动器还要占一块，留出余量反而更稳。
- 症状对照：游戏加载大地图或生成新区块时闪退退回启动器，多半是内存给少了；反之内存给太大导致系统杀后台，表现为整个游戏连同启动器一起被挤出后台。

手动分配没有官方标准值，下表是第三方资料与玩家实践中常见的起点，仅供参考：

| 设备运行内存 | 玩什么 | 手动分配参考起点 |
| --- | --- | --- |
| 3 GB 及以下 | 1.8.9 / 1.12.2 等老版本 | 1 GB 左右 |
| 4~6 GB | 1.16~1.20 原版 | 1.5~2.5 GB |
| 8 GB 及以上 | 新版本或轻量模组包 | 2.5~3.5 GB |

两点提醒：分配值不是越大越好，超过设备物理内存一半左右后，被系统整体杀后台的概率反而上升；第三方资料普遍建议玩 1.13 及以上版本用 4 GB 内存以上的设备，内存太小的机器优先靠降版本、降分辨率救帧数。

改完内存后重进版本生效。如果调整后仍然闪退，按 [闪退黑屏与登录报错处理.md](闪退黑屏与登录报错处理.md) 的对照表继续查。

## 四、两个影响流畅度的开关

在启动器设置里，这两个开关与帧数直接相关：

1. **sustained performance mode（持续性能模式）**：主动限制 CPU/GPU 峰值来抑制发热降频。长时间游戏帧数越跑越低时打开，短时间爆发性能会牺牲一些。
2. **alternate surface rendering（备用渲染表面）**：个别机型上能提升渲染速度或修复画面异常；如果你的设备一切正常，不用动它。

再加上触屏篇里的游戏内分辨率缩放，这三样就是手机上最常见的三个「帧数旋钮」。装模组之后如果帧数骤降，先确认渲染器是否匹配模组要求（见 [Forge与Fabric模组安装.md](Forge与Fabric模组安装.md)）。

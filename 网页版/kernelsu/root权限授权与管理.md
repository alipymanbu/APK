## 一、授权发生在哪里

应用第一次请求 root 时，KernelSU 管理器会弹授权确认，你可以选择允许或拒绝。所有已授权与被拒绝的应用都集中在管理器的「超级用户」页，随时可以回来改主意——把某个应用的授权关掉，它下次执行 `su` 就会被拒。

KernelSU 的授权判定在内核里执行，不是应用自己「自觉」遵守的规则，所以授权状态不依赖应用的配合，用户说了算。

## 二、App Profile：给 root 降权

对已授权 root 的应用，管理器里可以打开它的 App Profile（也叫 Root Profile），把「完整 root」修剪成「部分权限」。这是 KernelSU 相对其他方案比较有辨识度的能力，能配置的维度有四个：

### 2.1 UID / GID / 补充组

普通 root 是切到 UID 0（root 用户），App Profile 可以指定 `su` 之后实际生效的用户身份。典型用法：

- 给某个工具类应用只给 shell 权限：把 UID 设为 `2000`（ADB shell），它拿到的就是 shell 级权限而非完整 root；
- 去掉补充组 `inet`：这个 `su` 就无法访问网络——适合「只用它改本地文件、不需要联网」的场景。

注意一个容易误解的点：App Profile 管的是**这个应用执行 `su` 之后的权限**，不是应用本身的 Android 权限。应用自己申请的网络权限照常生效，跟 `su` 无关。

### 2.2 Capabilities（权能）

如果你需要应用执行 `su` 后仍是 UID 0，但不想让它为所欲为，可以裁剪 Capabilities——Linux 把「超级用户的特权」拆成了一个个独立单元（比如绕过文件读取检查的 `CAP_DAC_READ_SEARCH`），去掉哪个就少了哪类能力。每项 Capability 的含义可查 Linux 手册（`https://man7.org/linux/man-pages/man7/capabilities.7.html`），官方建议自定义前先读懂再动手。

### 2.3 SELinux 域

可以把应用执行 `su` 后的 SELinux 上下文从默认的 `u:r:ksu:s0` 切到自定义域，并为该域定制访问规则，实现更细的隔离。SELinux 规则写错会导致应用拿不到需要的权限，改之前建议了解 SELinux 的基本工作方式。

### 2.4 防逃逸：NO_NEW_PRIVS

一个实测会踩的坑：如果你给 ADB shell（UID 2000）开了允许 root，又把某个应用的 Root Profile 设成 UID 2000，这个应用可以**连续执行两次 `su`**——第一次被降权到 2000，第二次以 2000 身份请求时正好撞上「2000 允许 root」的规则，拿到完整 root，限制就失效了。给该应用的 Profile 启用 `NO_NEW_PRIVS` 标志可以堵住 KernelSU 这条提升路径，但它挡不住其他 Linux 机制的逃逸，所以根本上还是要合理设计权限。

## 三、对未授权应用：「卸载模块」开关

对没有 root 授权的普通应用，App Profile 里有一个「卸载模块」开关，决定内核和模块系统是否对该应用卸载模块挂载造成的修改。管理器设置里还有一个总开关「默认卸载模块」，默认**开启**——即不做单独设置时，所有普通应用都会被卸载模块修改。

两种配置思路，效果等价，选一种坚持用：

- **白名单式**：总开关保持开启，个别需要看到模块修改的应用，单独在它的 Profile 里关掉「卸载模块」；
- **黑名单式**：总开关关闭，个别敏感应用单独开启「卸载模块」。

一个版本相关的细节：在 5.10 及以上内核上，卸载动作由内核执行；5.10 以下的设备上这个开关只是配置项，KernelSU 本身不做动作，部分模块（如 Zygisksu）会读它来决定行为。配合模块使用时的整体逻辑见[模块与Zygisk使用指南](模块与Zygisk使用指南.md)。

## 四、日常管理的几条实用建议

- **按最小权限发授权**：给防火墙类应用只开网络相关能力、给冻结类工具只给 shell 权限，完整 root 留给确实需要的少数应用；
- **授权列表定期过一遍**：不再用的应用直接撤销授权，别让挂着的 root 成为隐患；
- **动了 Profile 之后先验证**：以该应用实际执行一次它要做的操作，确认权限够用也够窄；
- 授权和模块出问题导致的无法开机，处理路径在[常见问题与救砖方法](常见问题与救砖方法.md)；安装与管理器本身的问题回[下载与安装教程](下载与安装教程.md)。

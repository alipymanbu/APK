## 两类配对，别混着查

| 类型 | 管什么 | 入口 |
|---|---|---|
| 私信配对（DM pairing） | 谁能跟 bot 私聊 | 配对码 + Control UI 或 CLI 批准 |
| 设备配对（node pairing） | 哪台设备能加入 Gateway | 手机 / 桌面端的连接请求 + `openclaw devices approve` |

遇到「批准过了还不通」，先分清是「某个人发消息不通」还是「某台设备连不上」：前者查私信配对，后者查设备配对，排查思路见 [常见问题与排查.md](常见问题与排查.md)。

## 私信配对怎么运作

渠道的私信策略设为 `pairing` 时：陌生发信人会收到一个 8 位大写短码（不含 0/O/1/I 这类易混字符），你批准之前，他的消息不会被处理。Telegram 渠道默认就是这个策略；从建 bot 到批准第一条私信的完整链路见 [Telegram渠道接入步骤.md](Telegram渠道接入步骤.md)。要点：

- 码 1 小时过期；每位发信人大约每小时只收到一次配对提示；
- 每个渠道账号最多 3 条待审请求，挂满后新请求被忽略；
- 批准入口两个：Control UI 的 Settings → Channels → DM access requests（可按渠道筛选、能看发信人 ID），或命令行：

```bash
openclaw pairing list telegram
openclaw pairing approve telegram <CODE>   # 加 --notify 通知对方
```

注意一个隐藏坑：还没设过「命令所有者」时，用 CLI 批准会把这位发信人自动引导成首位所有者（写入 `commands.ownerAllowFrom`）。所有者能执行 `/update`、重启 Gateway、批准敏感命令——这个身份只该给你自己，别随手把别人批成所有者。批准私信访问也不等于给了群组权限，群组走单独的白名单。

## 白名单与访问组

不想走配对码的渠道，直接配 `dmPolicy: allowlist` 加 `allowFrom`；群组用 `groupPolicy` 加 `groupAllowFrom`。同一批信任的人要在多个渠道复用、或同时管私信和群组时，用 `accessGroups` 定义一次、处处引用，免得几份名单改着改着就不一致了。

这些名单存放在 Gateway 的 SQLite 状态库（`~/.openclaw/state/openclaw.sqlite`）里——把它当敏感数据对待，它就是助手家门的钥匙串。

## 手机端权限逐项管

安卓 app 的手机能力是逐项授权的：相机、照片、联系人、日历、通话记录、短信搜索、运动、已装应用、指定通知事件。取舍原则：你让助手帮你看什么，才开什么，用不到的当场关掉。连接与切换网关的操作见 [手机端配对与连接.md](手机端配对与连接.md)。

多台 Gateway 混用时留意：同一时间只有「焦点」网关能调用手机能力（相机、位置、屏幕、通知），这个设计就是为了防止两边的助手同时指挥你的手机。

## 远程访问的安全清单

手机出了门还要连家里的 Gateway，按这张清单核对：

| 做法 | 结论 |
|---|---|
| Tailscale Serve 或其他真正的 `wss://` 端点 | 推荐路线 |
| 同一局域网内 `ws://` | 可以接受 |
| 把 18789 端口直接暴露到公网 | 不要做 |
| 明文 `ws://` 走公网地址 | 不要做 |

各聊天渠道各自的接入材料与默认行为见 [支持的消息渠道一览.md](支持的消息渠道一览.md)；配对码过期、待审数量上限这些细节问题，在 [常见问题与排查.md](常见问题与排查.md) 里有对应条目。

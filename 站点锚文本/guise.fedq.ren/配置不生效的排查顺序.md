# 配置不生效的排查顺序

> 配置保存了、应用也重开了，参数却还是原值？本篇给一条从高频到低频的排查链：先查勾选与强停，再查框架状态，最后才怀疑参数本身。还不知道怎么配置的，先看[按应用改机型参数怎么配](按应用改机型参数怎么配.md)。

---

## 先过这四关

绝大多数"没效果"出在前两关，从上往下对：

| 顺序 | 检查点 | 判定与处理 |
| --- | --- | --- |
| 1 | 应用在 Guise 里勾了吗 | 勾选是启用开关。只保存配置不勾选不生效；配置清空保存还会自动取消勾选 |
| 2 | 应用被真正强停过吗 | 后台残留进程读的是旧配置。用系统「应用信息 → 强制停止」，从最近任务划掉不算 |
| 3 | LSPosed 里模块启用了吗 | 模块页里 Guise 应为启用状态；刚启用完的话重启一次手机排除框架未加载的情况，也可在 LSPosed 里打开 Guise 的作用域列表，确认目标应用在列 |
| 4 | 应用真读这些接口吗 | 有的应用走原生属性、IP 定位等覆盖不到的途径。先用靶应用验证注入是否成功，再判断是"没注入"还是"注入了但应用不读" |

补充一个容易卡住的点：在 Guise 里点「停止/重启」没反应时，新版本会按 ROOT → Xposed 服务 → 引导进系统应用信息页的顺序回退，照着引导走即可；任何版本下，「应用信息 → 强制停止」永远可用。

## 参数本身不被认怎么办

应用会校验参数自洽性：Android 版本与 SDK 对不上、Fingerprint 格式不对、机型组合太罕见，都会让目标应用弃用可疑值或改走别的取值途径。处理办法是换一套配套、常见的组合再试——用一键随机生成的成套值通常比手填的自洽，这个方法在[按应用改机型参数怎么配](按应用改机型参数怎么配.md)里有展开。

## 模块之间会打架

同一个目标应用同时挂了多个改设备信息的 Xposed 模块时，注入值可能互相覆盖。在 LSPosed 里暂时停用其他同类模块，只留 Guise 验证一轮，确认分工之后再决定怎么共存。

## 都试过还不行

- **看运行日志**：Guise 内置运行日志。强停并重开目标应用后找该应用包名的注入记录——有记录但值不对，是参数问题；完全没记录，回到上面第 1、3 关查作用域与框架。
- **换新版本**：模块在持续维护（2.0.0 起由 daxiaamu 接手），特定机型与系统组合的失效常在后续版本修复。
- **反馈问题**：确认是模块本身的问题，到项目的 GitHub 仓库提 Issue，附上机型、系统版本与日志。

还有一条容易被误判：部分应用对 Root/Xposed 环境本身敏感，勾选后表现为闪退或功能受限——这不是参数没生效，而是环境被应用察觉了，金融、游戏类带风控的应用尤其常见。这类风险在决定搭建环境前就该权衡，见[是什么模块与root前提](是什么模块与root前提.md)。

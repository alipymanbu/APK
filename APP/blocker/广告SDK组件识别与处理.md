# Blocker 广告与推送 SDK 组件的识别方法

> 本篇讲官方规则库没覆盖到的应用，怎么靠组件类名前缀自己识别广告、推送、统计 SDK 的组件，以及识别之后的处理顺序和证据边界。

Blocker 的规则库收录了常见广告 SDK（腾讯广告、穿山甲、快手广告联盟、百度移动推广等）的组件规则，但总有一些应用用的是冷门 SDK 或新版本，库里没有现成规则。这种情况你要自己动手判断——判断的主要依据就是组件的类名前缀。

## 一、识别原理

应用集成某个 SDK 后，SDK 的组件（service、receiver、provider）会以该 SDK 的包名作为类名前缀出现在组件列表里。比如集成了穿山甲的应用，组件列表里会出现大量 `com.bytedance.sdk.openadsdk` 开头的组件。看到前缀，就能反推出它属于哪家 SDK、大致是干什么的。

## 二、常见 SDK 类名前缀对照

下表按官方 SDK 文档与 SDK 隐私声明整理，供识别参考。SDK 会随版本调整包名，实际判断以组件详情里的类名与说明为准：

| SDK | 常见类名前缀 | 主要用途 |
| --- | --- | --- |
| 优量汇（广点通，腾讯广告） | `com.qq.e.ads`、`com.qq.e.comm` | 广告展示 |
| 穿山甲（Pangle，字节广告） | `com.bytedance.sdk.openadsdk` | 广告展示 |
| 快手广告联盟 | `com.kwad.sdk` | 广告展示 |
| 百度移动广告 | `com.baidu.mobads` | 广告展示 |
| AdMob（谷歌广告） | `com.google.android.gms.ads` | 广告展示 |
| Mintegral | `com.mbridge` | 广告展示 |
| 友盟统计/推送 | `com.umeng` | 统计、推送 |
| 个推 | `com.igexin` | 推送 |
| 极光推送 | `cn.jpush` | 推送 |
| 华为推送 | `com.huawei.hms.push` | 推送 |
| 小米推送 | `com.xiaomi.push` | 推送 |
| OPPO 推送 | `com.heytap.msp.push` | 推送 |
| vivo 推送 | `com.vivo.push` | 推送 |
| 移动安全联盟 OAID | `com.bun.miitmdid` | 设备标识 |

同一应用常同时集成多家 SDK：广告 SDK 负责弹广告，推送 SDK 负责拉活跃，统计 SDK 负责埋点。它们互相唤醒，关掉推送通道经常能连带减少广告唤醒。

## 三、处理顺序

1. **过滤**：在应用组件列表里按上表前缀（或 `ad`、`push` 等短词）搜索过滤；
2. **逐个查看**：点开组件看完整类名与说明，确认用途与归属；
3. **先动 receiver 和 service**：广告与推送 SDK 的活跃点大多在这两类；activity 关多了界面会缺功能；
4. **验证**：回到应用确认广告减少、功能正常（验证方法见 [组件禁用操作指南.md](组件禁用操作指南.md)）；
5. **记录**：调整完导出一份规则存底（方法见 [规则导出导入与备份.md](规则导出导入与备份.md)），下次重装或换机直接导入。

## 四、证据边界

- 上表前缀是**识别参考**，不是禁用依据；SDK 大版本更新可能换包名，冷门前缀先查证再动手；
- **统计类组件谨慎关**：友盟等统计组件常被应用用于崩溃上报，关掉后应用出错时开发者收不到反馈，个别应用还会对统计组件做存活检测；
- 厂商推送通道（华为/小米/OPPO/vivo）关掉后，该厂商渠道的通知可能收不到，按需取舍；
- 关完应用异常，按 [常见问题与报错处理.md](常见问题与报错处理.md) 与恢复流程处理（见 [组件误禁用后的恢复步骤.md](组件误禁用后的恢复步骤.md)）。

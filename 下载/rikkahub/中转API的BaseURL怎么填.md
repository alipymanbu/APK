# 中转API的BaseURL怎么填

> 用中转/聚合类服务时，最常见的故障不是密钥错，而是 Base URL 与 API 格式没对上。本篇把这块拆开讲，配完再看排查清单。

## 一、Base URL 填的是服务商给的确切地址

Base URL 不是随手写的域名，要以服务商后台给出的「接口地址」为准：

- 一般形如 `https://xxx.example.com/v1` 这样的完整前缀，**结尾的路径段（`/v1`、`/v1beta` 等）必须照抄**，少一段、多一段、结尾多一个斜杠，都可能导致请求 404 或全部模型连不上；
- 服务商文档里若分开给「OpenAI 格式地址」「Gemini 格式地址」，那是两个不同入口，别混用。

## 二、同一个 key，为什么有的模型通有的不通

不少中转平台把不同厂商的模型放在**不同渠道类型**下：第三方教程里被反复提到的一个坑就是 `/v1` 与 `/v1beta` —— `/v1` 一般对应 OpenAI 兼容通道（GPT、Claude 等都走它），`/v1beta` 往往只服务 Gemini。同一个 key 在电脑端全通、到 RikkaHub 里只有 Gemini 能用，多半就是这里没对上。

对策很直接：

1. 看清服务商后台每个模型条目标注的渠道类型；
2. **每种渠道类型在 RikkaHub 里单独建一个服务商条目**，各填各的 Base URL，别在一个条目里混填。

## 三、兼容格式与原生格式怎么取舍

| 选择 | 适合 | 代价 |
| --- | --- | --- |
| OpenAI 兼容格式（默认） | 绝大多数中转、聚合服务，一个 key 调多家模型 | Gemini 的思维链、Claude 的一些原生特性可能表现不完整 |
| Google / Anthropic 原生格式 | 想要对应厂商的完整能力（如思维链） | 中转平台要走它单独给的 Gemini/Anthropic 地址 |

多个独立教程给出的建议一致：日常用兼容格式最省事；对某家模型有完整能力要求时，再为它单独建原生格式的条目。

## 四、模型拉取不到就手动填

用中转地址时，「自动拉取模型列表」不一定能出全（走原生格式的中转尤其常见）。处理办法：

1. 到服务商后台的模型列表页，抄下**准确的模型 ID**（大小写、版本号都要一致）；
2. 回 RikkaHub 的服务商配置里手动添加这个模型名；
3. 模型 ID 拼写错误的表现通常是「模型不存在」或请求 404，逐字符核对即可。

## 五、排查清单

| 症状 | 先检查 |
| --- | --- |
| 所有模型都连不上 | Base URL 是否照服务商后台逐字符填对；结尾路径段 |
| 只有 Gemini 通，GPT/Claude 不通 | 渠道类型：这两类该走 `/v1`（或服务商指定的 OpenAI 兼容地址），不是 Gemini 那个地址 |
| 报「模型不存在」/ 404 | 手动填的模型 ID 是否与后台完全一致 |
| 能聊天但没有思维链等完整能力 | 该模型换原生格式条目再试 |
| 以前能通突然不通 | 服务商改过地址/下架过模型，回后台核对公告 |

逐项查过仍不行的，回服务商后台确认服务本身可用，再到 [常见问题与解决方法.md](常见问题与解决方法.md) 过一遍通用排查；基础配置步骤在 [服务商与API密钥配置.md](服务商与API密钥配置.md)。

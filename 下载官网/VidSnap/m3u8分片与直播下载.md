现在多数在线视频不是「一个地址对应一个完整文件」，而是被切成许多几秒钟的小片段连续下发，地址那头只有一份索引文件（扩展名 `.m3u8`，部分站点用 `.mpd`）。VidSnap 把这类流接住之后，会先把片段一个个下下来，再合成一个完整视频。直播流走的是同一套机制，区别在于片段还在持续产生，所以它只能边播边录。这两类下载的失败现象和整段 MP4 完全不同，值得单独说清。

## 一、分片流和普通视频的区别

| | 整段视频（MP4 类） | 分片流（M3U8 / MPD 类） |
| --- | --- | --- |
| 地址指向 | 一个完整的视频文件 | 一份索引，里面列着几十到几千个小片段 |
| 下载过程 | 一次请求拉完 | 逐个（或按线程分段）拉取片段 |
| 下载耗时 | 取决于带宽与文件大小 | 除带宽外，还受「片段数量 × 单次请求耗时」影响，碎片多时明显更慢 |
| 失败表现 | 文件小得离谱、播到一半停住 | 片段缺失、合并后时长不对、花屏、只有声音没有画面 |
| 能否边下边播 | 通常可以 | 要等合并完成后才是一个可用文件 |

所以在 VidSnap 里看到「进度条走得慢、最后几步卡很久」，是正常现象——后半段往往在做收尾和合并，不是在重复下载。

## 二、下载分片流时实际发生了什么

1. 检测到索引地址，应用读取它，知道片段的数量和顺序；
2. 逐个请求片段，全部落到本机；
3. 把片段按顺序拼成一个视频文件，下载完成，出现在「下载」标签里。

这三步里，第 2 步最怕网络抖动：**中途断网会让某几个片段缺失，片段缺了合并出来的文件就可能在对应位置卡住或花屏。** 断点续传能补上后续进度，但如果那次断网正好让某个请求彻底失败，重下一次比修补更省事。

另外，别在下载过程中去刷新或关闭那个播放页面。应用本身支持退到后台继续下载，切去别的应用没关系（被系统省电策略清掉后台是另一回事，见 [常见问题与排查.md](常见问题与排查.md) 第二节）；但把页面本身关掉，部分站点会让已建立的片段请求失效。

## 三、直播下载为什么不同

直播没有「总长度」这个概念：你点下载的时候，能拿到的只是**从这一刻开始往后新产生的片段**——已经播过去的画面不会回溯。所以直播下载本质上是「边播边录」：

- 录多久，文件就有多长，停止下载即结束录制；
- 录制期间必须保持网络连通，断流的那一段就是永久缺失，补不回来；
- 录制中的文件要等停止后才合成完成，中途退出去看「下载」标签，可能只看到一个还在增长的任务。

由此带出两条实操建议：

- **优先用稳定的 Wi-Fi**。直播录制对连续性最敏感，手机信号切换一次往往就丢一段。
- **空间先留够**。一场直播录下来体积可能远超你平时下的短视频，动手前看一眼剩余存储空间。

## 四、按现象对照处理

| 现象 | 最可能的原因 | 处理 |
| --- | --- | --- |
| 下载完成但播放到某处卡死、花屏 | 多线程下载或片段请求失败 | 把「常规文件线程数」改成 1，重下一遍，见 [设置项与嗅探规则怎么调.md](设置项与嗅探规则怎么调.md) |
| 时长明显比原视频短 | 录制期间断过流（直播），或部分片段没下到 | 直播只能重录；分片流重新下载 |
| 只有声音没有画面，或反过来 | 该站点把音视频分成两条流下发，其中一条没被接住 | 重新检测一次，等两条流都出现在结果里再下载 |
| 合并后文件能播但拖进度条异常 | 分片边界处的时间信息接不上 | 重下一遍；仍然如此就换单线程再试 |
| 音画越播越偏、长视频后段不同步 | 源头的分片时间戳本身不连续 | 见下面这段，多数情况修不好 |
| 直播录到一半停止 | 网络中断，或应用被系统后台清理 | 网络中断只能重新录；后台被清的处理见下面第五节第 2 条与 [常见问题与排查.md](常见问题与排查.md) 第二节 |

**关于音画不同步。** 这一类问题和下载操作关系不大，动手重下之前值得先分清来源：

- **音视频被拆成两条流下发**：现在很多站点把画面和声音放在各自独立的索引里，播放器负责对齐，下载时若只接住一条，结果就是有声无画或有画无声。这种可以靠「重新检测一次、确认两条都被接住」解决。
- **分片自身的时间信息不连续**：每段分片里都带着音频与画面各自的时间标记，源头切分得不规整时，单独看每一段都正常，拼成完整视频后误差会逐段累积——表现是越播越偏；拖进度条之后错位更明显，因为跳过去的那一段缺少前面的时间基准。这种偏差在源头就存在，重下同一档通常修不好，能做的只有换一个来源或者放弃这一段。

判断顺序就按上面两条走：重下一次仍然错位，基本可以确认不是下载环节的问题。

## 五、提高成功率的四条

1. **线程数保持 1**。分片流和直播对请求顺序更敏感，单线程是最稳的档位。
2. **下载期间别让系统清掉后台**。部分定制系统会定期清后台应用，正在录制的直播会因此中断，具体要动哪几个开关见 [常见问题与排查.md](常见问题与排查.md) 第二节。
3. **一次别同时开太多任务**。分片流的请求量本来就大，几条一起跑会互相抢带宽，反而更容易失败。
4. **空间先留够**。分片流与直播录制的体积比短视频大得多，而且空间不足要到最后的合并阶段才报错，前面的片段全部白下；核对方式见 [下载的视频存在哪.md](下载的视频存在哪.md)。

剩下的通用问题——比如下载完了找不到文件、想批量下、换手机之后视频怎么带走——放在 [常见问题与排查.md](常见问题与排查.md)。分片流抓不到的情况（连索引都没接住）不属于本篇，去 [视频检测不到怎么办.md](视频检测不到怎么办.md)。

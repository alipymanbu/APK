# HopToDesk 自建服务器怎么弄

## 一、什么时候值得自建

官方明确支持自托管：你可以在自己的服务器或现有基础设施上搭一套私有的 HopToDesk 网络。值得动手的典型情形：

- 内网 / 隔离网络里的设备互连，不想经外部中转；
- 对「信令与中转由谁运营」有合规或自主要求；
- 自家机房到被控设备的链路比公共中继更近，想要更低延迟。

不需要自建也能正常用——默认网络对所有用户开放，自建是进阶选项。

## 二、路线一：自己的 Linux / Windows 服务器

官方提供一键脚本方式（兼容 Ubuntu 18–24 和 Windows），核心是部署一个名为 **HopSignal** 的信令服务：

1. 在服务器上执行官方安装脚本（官网 On-Premises 页面提供，脚本从官方地址拉取 `hopsignal` 二进制并注册 systemd 服务）；
2. 脚本默认监听 80 端口做信令，可按需传入自定义 TURN 中继的四个参数（主机、端口、用户名、密码），不传则继续用官方默认中继；
3. 装完后脚本会打印服务器的信令地址，这个地址就是客户端要填的对接值；
4. 脚本自带 cron 自检（WebSocket 掉线自动重启、日志超限轮转），防火墙记得放行 80 端口（脚本会尝试代配 ufw）。

部署形态有两种：

| 形态 | 行为 |
| --- | --- |
| LAN + 默认中继 | 局域网内设备直连，出外网的连接仍走 HopToDesk 官方中继 |
| 自定义 TURN | 连中继也换成自己的，全链路自家设备 |

## 三、路线二：Cloudflare Workers

不想管服务器的话，官方给出了把信令架在 Cloudflare Workers 上的做法：

1. 登录 Cloudflare，进入你的域名 zone，新建一个 Worker；
2. 把官方提供的 Worker 代码（`hopsignal.js`，官网 On-Premises 页可取）粘贴进 `index.js`，保存并部署；
3. 得到的 Worker URL 就是客户端要填的 `rendezvouswss` 值。

注意一个硬前提：这套 Worker 用到了 Durable Objects，**需要 Cloudflare 付费方案（每月 5 美元起）**，免费套餐跑不了。

## 四、路线三：AWS Marketplace

官方在 AWS Marketplace 上架了镜像：订阅 → 配置 → 启动实例，Amazon 把服务拉起来之后，把实例的 https 地址设为客户端的 `rendezvouswss` 值即可。适合已经在用 AWS、不想自己维护进程的场景（实例本身按 AWS 计费）。

## 五、客户端怎么指向你的网络

两种配法（官方帮助中心口径）：

1. **发布 api.json**：把配置文件（含信令地址与 TURN 参数）发布到你自己的 URL，然后在 HopToDesk 客户端的 **Choose Network** 区域选中这个 URL；
2. **本地 api.json**：在 HopToDesk 的配置路径下放一个 `api.json`，写入 `rendezvous`（信令主机与端口）与 `turnservers`（中继参数）等字段。

配好后客户端的连接就走你自己的信令 / 中继了。改动只影响你控制的客户端——远端那台设备也要用同一套网络配置，两端才碰得上头。

## 六、自建之后检查什么

- 两台设备分别连一次，确认会话能建立（说明信令通了）；
- 局域网内互连看是否直连成功；外网互连确认中继路径可用；
- 服务器侧看 `hs.log` 与 systemd 状态（脚本路线），Workers 路线看 Cloudflare 的 Worker 日志。

连接正常但体验异常时，回到 [连接失败排查](连接失败排查.md) 先排除两端软件状态，再回来看服务器配置。
